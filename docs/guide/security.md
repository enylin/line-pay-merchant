# 安全性

付款整合的風險大多不在函式庫，而在流程。這份清單是上線前要逐項確認的事。

## 你要做的

**1. 金額來自你的資料庫，不是網址。**`confirm` 的 `amount` 要用訂單上的金額。網址上的任何參數都是用戶的瀏覽器給的。

**2. 用 `parseConfirmQuery()` 解析 `confirmUrl` 的參數。**

```ts
const { transactionId } = parseConfirmQuery(req.query)
```

它只接受恰好一個、1 到 19 位數字的 `transactionId`，其餘（多個值、陣列、物件、路徑符號、SQL 片段）一律丟 `LinePayValidationError`。然後用你呼叫 `request` 時存下的 `transactionId` 在**你的資料庫**找訂單，找不到就是 404。不要用網址上的 `orderId` 當依據：瀏覽器可以把任何 `orderId` 配上任何 `transactionId`，所以用 `orderId` 找訂單、卻拿網址上的 `transactionId` 去 `confirm`，可能讓一張便宜的訂單被別人那筆已核准的付款付掉。如果你一定要用 `orderId` 找，請先檢查 `order.transactionId` 就是網址上的那個 `transactionId`。

**3. `confirmUrl` 要能安全地被重複呼叫。**用戶會重新整理、按上一頁，網址也可能被轉寄。檢查訂單狀態：已經 `paid` 就直接回結果，不要再打 `confirm`。同時湧入的請求用條件更新搶佔（見[範例](/recipes/)）。

**4. 結果未知時對帳，不要重送。**見[結果未知與對帳](./unknown-outcome)。

**5. 金鑰只放伺服器。**用環境變數或密鑰管理服務，不要提交到 Git，不要送到瀏覽器。懷疑外洩時，到商家後台重新產生並更新部署。

**6. confirmUrl 與 cancelUrl 用 https，而且固定寫在設定裡。**不要用請求的 `Host` 標頭組出來：偽造的 `Host` 會把用戶（和那筆交易）送到別的網站。

**7. 退款要有權限控管。**退款會動到錢。用[middleware](./middleware#擋掉某個操作)把只該由特定服務執行的操作擋在其他地方之外，並記錄是誰、為何發起。同一筆付款的退款要排隊（加鎖）：同時發兩筆同金額的退款，對帳分不出哪一筆是哪一次呼叫（見[結果未知與對帳](./unknown-outcome#退款要特別小心)）。

**8. 發起付款的路由要驗證身分，確認訂單是這個用戶的。**`startCheckout` 的網址、`confirmUrl` 之後顯示訂單的頁面，都是公開的網址。發起前確認登入的用戶擁有這張訂單；表單型的請求要有 CSRF 防護。範例（`examples/express.ts`）為了只留下 LINE Pay 的部分，**沒有**這些。

**9. 對外的 confirm 路由要限流**，並且確認回來的 `transactionId` 屬於你的某張訂單，才去碰 LINE Pay（範例的 `unknown-order` 在呼叫 LINE Pay 之前就回 404）。

**10. 履約只做一次。**搶佔成功的請求、搶輸的請求、每一次重新整理、背景工作，都可能看到「已付款」。不要把出貨、寄信、加點掛在每一次看到 `paid` 上：掛在「這個行程把訂單從 `confirming` 改成 `paid`」的那一次（範例的 `onPaid`）。行程可能在更新與履約之間掛掉，所以要做到不漏，把待辦寫進與更新同一個資料庫交易裡（outbox）。

**11. 確認付款是這張訂單的。**`confirm` 成功（或對帳 `applied`）之後，拿回應的 `info.orderId` 跟你送給 `request` 的訂單編號比對，不符就不要標成已付款（範例把它存在訂單上，不符就轉給人處理）。

**12. `regKey` 是憑證。**預先授權付款的 `confirm` 回應裡有 `regKey`：加密存放（或存進密鑰管理服務），限制誰讀得到，不要寫進日誌、錯誤回報或分析工具；`body` 是一般物件，不會自動遮蔽。用戶移除付款方式時呼叫 `expireRegKey`。

**13. 編號存成文字，不要存成數字。**`transactionId` 有 19 位數字，超過 2^53：存進 `BIGINT`、再被驅動程式讀成 JavaScript 的 `number`，末幾位就悄悄變了；變了的編號仍是 19 位數字，會通過檢查，退款就會對著另一筆交易送出。用 `TEXT` 或 `VARCHAR` 欄位，`orderId` 也一樣（可能有前導零）。見[兩個編號](./payment-flow#兩個編號)。

## 函式庫替你做的

| 防護                     | 說明                                                                                                                                                                                                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 路徑參數一律驗證         | `transactionId` 只允許 1–19 位數字、`regKey` 只允許英數字，並且編碼後才放進路徑，即使 `validate: false` 也一樣。0.9 把它們直接塞進路徑，`../` 可以改寫簽章過的路徑。                                                                                                 |
| 簽「實際送出的字串」     | 簽章涵蓋的就是送出的內容：查詢字串是照 URL 解析器的結果簽的，而送出的也正是那個 URL，所以序列化的差異（例如單引號被改寫成 `%27`）不會讓兩者不一致。                                                                                                                  |
| 輸入在呼叫當下複製一份   | 重試和對帳用的 context 都讀這份複本。呼叫端接著拿同一個物件去做下一筆，不會改變前一筆重送的內容，也不會讓對帳去查錯付款。只收純資料：class 實例、getter、不可列舉的欄位複製時會悄悄少掉（退款少了 `refundAmount` 就是全額退款），所以直接拒絕。                      |
| 不認得的欄位會被拒絕     | 拼錯的 `refundAmout`、多送的 `customerEmail` 不會被簽名後送給 LINE Pay（`validate: false` 時除外）；退款的金額檢查則永遠開著。                                                                                                                                       |
| 回應先檢查，才有型別     | 每個操作的回應都用型別守衛逐欄位檢查過，才交給你；缺欄位或型別不對的，是一個 `unexpected-shape` 錯誤（結果 `unknown`，要對帳），而不是一個型別是謊言的值。整個專案沒有 `as` 與 `!`。                                                                                 |
| 回應有大小上限           | 回應最多讀 8 MiB，超過就停止（`body-too-large`），不會被一個沒有盡頭的回應塞爆記憶體。                                                                                                                                                                               |
| 設定只讀物件自己的屬性   | 被污染的 `Object.prototype.baseUrl` 不會讓簽過章的請求送到別的主機。                                                                                                                                                                                                 |
| `regKey` 不進 context    | `regKey` 是憑證；對帳用 `orderId` 查，所以不需要它，也不會被記進錯誤。                                                                                                                                                                                               |
| 不跟隨轉址               | 自訂的 `X-LINE-Authorization` 標頭不會被轉送到別的來源。                                                                                                                                                                                                             |
| 19 位數編號不失真        | 超過 2^53 的整數在解析時轉成字串。                                                                                                                                                                                                                                   |
| 錯誤與 client 不洩漏秘密 | 錯誤的 `toJSON()` 是白名單，`console.log(error)` 與 `util.inspect` 印的也是同一份（外加堆疊），不含回應內容與 context；`error.body`、`error.bodyText` 與 `error.context` 不可列舉，複製錯誤物件屬性的記錄工具不會把它們寫下來；client 只有方法，序列化不會帶出金鑰。 |
| `baseUrl` 限制 https     | 只有 localhost 可以用 http。                                                                                                                                                                                                                                         |
| 重試只在證明安全時發生   | 見 [Middleware](./middleware#retrywhennotsent)。                                                                                                                                                                                                                     |

## 回報安全問題

請不要在公開的 issue 貼金鑰或可利用的細節。到 [GitHub 的 Security 頁面](https://github.com/enylin/line-pay-merchant/security)用私下回報。如果那裡沒有回報按鈕，請開一個 issue，只寫「我有一份安全問題的回報」，不要寫細節，等維護者提供私下的管道。
